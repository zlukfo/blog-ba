**Атрибут** - это свойство сущности, которое имеет имя и тип. 

>[!Почему важно понимать атрибуты]
> Прежде всего, потому что любая сущность определяется через множество атрибутов.
> Понимание атрибутов необходимо для проектирования и рефакторинга баз данных ,

Сущность "Бронирования" ==в демо базе== определяется тремя атрибутами:

| название     | описание                  |
| ------------ | ------------------------- |
| book_ref     | номер бронирования        |
| book_date    | дата бронирования         |
| total_amount | полная сумма бронирования |
Сущность "Бронирование" можно расширить, добавив например такие атрибуты, как номер терминала с которого было выполнено бронирование и индивидуальный номер кассира, создавшего бронь.

С другой стороны, атрибут total_amount (полная сумма бронирования) не является очевидным свойством данной сущности, он напрямую зависит от даты бронирования, например, если бронирование было выполнено в период действия скидок от авиакомпаний, полная сумма бронирования будет меньше. Для включения атрибута  total_amount в описание сущности нужны основания.

Приведенные примеры показывают, что при определении сущности в нее нужно добавлять только те атрибуты, которые наилучшим образом будут решать задачи бизнеса. 

Для этого есть несколько правил, которых рекомендуется придерживаться.

>[!Правило 1]
>Один или несколько атрибутов **должны входить** в состав потенциального ключа.
>*Потенциальный ключ* - это уникальный идентификатор, который однозначно идентифицирует экземпляр сущности.

Потенциальный ключ может состоять из одного или нескольких атрибутов. Например:
- если мы уверены что номер бронирования всегда уникален - book_ref является потенциальным ключом, состоящим из одного атрибута 
- если наша база содержит данные нескольких систем бронирования, то уверенности в уникальности номера бронирования нет - номера бронирования уникальны только в пределах одной системы бронирования, если их в базе несколько, они могут дублироваться. В этом случае мы должны добавить дополнительный атрибут, например идентификатор системы бронирования. Тогда потенциальный ключ будет состоять из двух атрибутов - {система бронирования, номер бронирования} 

Сущность может иметь один или несколько потенциальных ключей. Например, сущность "Гражданин России" включает атрибуты ИНН, СНИЛС, каждый из которых является самостоятельным потенциальным ключем

==Последний пример можно развить: список существующих систем бронирования может являться отдельной сущностью и атрибут "идентификатор системы бронирования" может принимать значение которое **должно соответствовать** одному из экземпляров этой сущности. Такой атрибут называется внешним ключом. *То есть, атрибутом потенциального ключа может являться внешний ключ*==   

>[!Правило 2]
>Если из атрибутов сущности нельзя составить ни один потенциальный ключ - в качестве потенциального ключа **нужно добавить** суррогатный атрибут.
>*Суррогатным* называется атрибут, который не соответствует никакому свойству объекта реального мира.

>[!Правило 3]
>Атрибут сущности может иметь любой тип и любую семантическую сложность если это эффективно решает бизнес-задачу  

Простой пример: ФИО человека это один атрибут или три (фамилия, имя, отчество)? 
- если нужно получать данные в формате "фамилия-инициалы", имеет смысл включить в сущность три атрибута
- если нужен поиск ФИО по запросу - его проще организовать по данным, хранящимся в одном атрибуте
- в описание сущности можно включить оба варианта хранения ФИО - но тогда придется решать задачу синхронизации данных при изменении значения одного из атрибутов

Другой пример: как хранить реквизиты компании? Здесь при выделении отдельного атрибута под каждый реквизит придется учитывать:
- однородность данных атрибута: ИНН для юридических лиц состоит из 10-и цифр, индивидуальных предпринимателей - из 12-и, алгоритмы проверки контрольных цифр у них разные
- обязательность атрибутов: КПП для юридических лиц обязателен, у ИП его нет
Альтернативным решением является введение одного атрибута "реквизиты компании", например с типом JSON.

Выбор варианта также зависит от бизнес-задач, например: будет ли являться ИНН первичным ключом сущности, насколько важно обеспечить компактное хранение данных, как быстро должен выполняться поиск по атрибутам, и так далее
